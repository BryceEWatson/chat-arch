# Project Identity v2 — design & implementation plan

Status: PROPOSED (revised after adversarial review round 1). Supersedes the
current single-rule `inferProject` classifier.

> Revision note (v2.1): Round-1 adversarial review cut the speculative
> machinery from the first draft. Guiding principle, restated: **"best" means
> every component traces to a *counted* failure mode and carries no correctness
> bug — not "most layers."** Components that targeted uncounted or
> zero-in-corpus signals are DEFERRED with explicit re-trigger conditions
> (§14), not abandoned. What survived is leaner, correct, and verifiable.

## 1. Architecture overview (revised)

`inferProject` becomes a small attribution pipeline returning
`(projectId, resolvedVia, confidence)`. Five components, each tracing to a
counted failure:

1. Parse-boundary filter — drop 0-turn sidecars; capture `parentSessionId`.
2. Signal propagation — surface `scheduledTaskId` + `sessionType` (confirm
   `userSelectedFolders` already lands).
3. A 6-step **strict first-match** cascade.
4. Trimmed provenance record `{resolvedVia, confidence}`.
5. User-override config (`sessionIds` | `cwdGlob`).

Plus: dry-run/preview mode, an audit+adversarial validation script, and a
rebuild-from-scratch migration (no alias system, no re-key passes).

## 2. Component 1 — parse-boundary filter

In `cli.ts` (and `cowork.ts` for invariance), before a session enters the
manifest: skip when **`userTurns === 0 && assistantTurns === 0 && !cwd && !project`**.
The `&& !cwd && !project` clause is load-bearing — **verified against the live
manifest**: there are 599 zero-turn sessions, but 36 carry a real `cwd` (24 of
them chat-arch). A naive "drop all 0-turn" would silently strip those 24 from
the chat-arch project. The gated predicate drops exactly the 563 true phantoms,
which are exactly the 563 currently-UNASSIGNED, all of which are
`titleSource:'ai-title'` (the corroborating shape signal — the predicate and
the `titleSource==='ai-title'` filter yield the identical 563 set).

The cli-direct aggregate already tracks `userTurns`/`assistantTurns`
(cli.ts:~86,88, emitted :733,739), so the filter is keyable; entries are
currently emitted unconditionally (cli.ts:722-753) — that is the phantom root
cause.

Capture `parentSessionId` when a session was spawned by another (`claude -p`
tool-use). The filtered 0-turn children are dropped from the session list; we
record only a count + parent linkage for the deferred subagent-attribution
feature (§14). Emit `parserSkips: { reason: '0-turn-sidecar', count, byParent }`
in the rescan summary for auditability.

**Determinism / equivalence to verify in the audit script:** that the gated
drop set (0-turn ∧ no-cwd ∧ no-project) == the prior UNASSIGNED set (both 563),
so the 563 phantoms are removed from the UNASSIGNED set (the post-rescan
UNASSIGNED residue is ≤ ~6 with reasons, per §0/§12 — not 0), AND that no
previously-populated project loses sessions (chat-arch must keep its 24
cwd-bearing 0-turn sessions).

## 3. Component 2 — signal propagation (new optional `UnifiedSessionEntry` fields)

```ts
scheduledTaskId?: string;   // READ from raw cowork manifest (not currently parsed) + spread onto entry
sessionType?: 'scheduled' | 'interactive' | string;  // same
parentSessionId?: string;   // from claude -p spawn linkage
```

`userSelectedFolders` and `cwdKind` ALREADY exist on the entry
(unified.ts:346, :136; cowork sets them at cowork.ts:624,647-649) — no
propagation work, only consumption in §4.

**Explicitly NOT added** (deferred — §14, and PII-driven cuts): `gitRemoteOriginUrl`,
`gitRoot`, `nearestManifest`, `cliProjectDirBasename`, `cloudProjectUuid`,
`systemPromptHash`, `initialMessageHash`. The hash fields are cut outright:
no cascade rule consumes them and a bare hash of a low-entropy prompt is a
stable correlator (confirm-by-guessing), not "PII-safe."

## 4. Component 3 — the 6-step cascade (strict first-match, confidence monotonic)

Governance is **strict first-match by order**. Confidences are monotonically
non-increasing down the list so the ordering and the confidence agree (the
first draft's confidences contradicted the order — fixed here).

```
0. user override (projectOverrides.json: cwdGlob | sessionIds → projectId)        1.00
1. explicit session.project                                                       1.00
2. scheduledTaskId   → proj_routine_<slug(scheduledTaskId)>                        0.90
3. cwdKind==='vm' && userSelectedFolders[0] non-empty → basename(USF[0])          0.80
4. cwd basename (today's rule; with VM-haiku guard below)                         0.50
5. title-keyword regex (today's rule)                                             0.40
6. __unassigned__                                                                 0.00
```

**Rule 2 keys the id on `scheduledTaskId`, NOT `slug(title)`.** This fixes both
the rename-split hazard and the slug-collision hazard. **Verified against the
raw Cowork manifests on disk:** 15 distinct `scheduledTaskId` values cover the
99 `outputs` sessions, and the values are already human-readable slugs
(`shopforge-daily-metrics-sync`, `pinterest-daily-pins`, …) — so the routine id
splits the 99 into ~15 stable routine projects.

**id-prefix discipline (avoid double-prefix + know the normalization):** every
cascade rule returns a *raw* key; `discoverProjects`'s `stableProjectId`
(discoverProjects.ts:145-151) lowercases, runs `.replace(/[^a-z0-9]+/g, '-')`,
and adds the single `proj_` prefix. Two consequences the implementer must hold:
(1) rule 2 returns `routine_<scheduledTaskId>`, NOT a pre-prefixed `proj_routine_…`
(which would mangle into `proj_proj-routine-…`); (2) **`stableProjectId`
collapses the `routine_` underscore to a hyphen**, so the emitted id is
`proj_routine-shopforge-daily-metrics-sync` (hyphen after `routine`, not
underscore). The namespacing point still holds: `proj_routine-chat-arch` ≠ the
cwd-derived `proj_chat-arch` — no cross-rule id collision. Because the on-disk
prefix spelling (`proj_routine-`) is an artifact of the normalizer, the audit
(§12) keys on `resolvedVia`, not an id-string prefix grep.

**displayName is derived deterministically, NOT taken from the first-match
title.** Verified hazard: one `scheduledTaskId` spans many per-run titles, each
date-prefixed (`shopforge-daily-metrics-sync` → "Mar 28 – Shopforge daily
metrics sync", "Mar 29 – …", …). Rule: `displayName` = the most frequent title
after stripping a leading date prefix (`/^\w{3,}\s+\d{1,2}\s+[–—-]\s+/` — note
the class covers hyphen, en-dash U+2013, and em-dash U+2014, since Cowork
auto-titles may use any), ties broken lexicographically; fallback = title-cased
`scheduledTaskId`. This is stable across rescans regardless of which run is
encountered first.

**Rule 3** routes VM sessions to their real host folder via `basename(USF[0])`.
Because the common case basenames match the host cwd basename (`chat-arch` VM
USF → `proj_chat-arch`, same as host sessions), this *also* achieves
cross-source unification for the measured cases — without a canonical map. (The
map only helped when basenames diverge, e.g. worktrees — uncounted; deferred
§14.)

**Rule 3 basename over-merge — trade-off, decided.** Basename can over-merge two
distinct host folders sharing a basename (`~/work/client-a/docs` vs
`~/personal/docs`). The alternative (last-2 path segments as the id key) would
*fix* that but *break* the cross-source unification basename gives us (host
`Projects/chat-arch` vs VM `user/chat-arch` would no longer match). The measured
VM-USF folders collapse to 16 distinctive names (`chat-arch`, `dropKnowledge`,
`Taxes`, `Finances`, `ShopForge`) with no observed collision, so basename is the
right grain for the data. The over-merge case is therefore handled by
*detection* (audit + adversarial experiment, §12) plus the *manual override
escape hatch* (component 5, `sessionIds`/`cwdGlob`), NOT by silently switching
to last-2-segments and regressing the counted cross-source case.

**Rule 4 VM-haiku guard:** when `cwdKind==='vm'` and rule 3 did not fire
(no `userSelectedFolders`, ~10 sessions), do NOT accept the haiku basename as
a project; fall through to rule 5. Regex (secondary explainer, the
`cwdKind==='vm'` gate is primary): `^[a-z]+-[a-z]+-(?:[a-f0-9]{6,}|\d{3,}|[a-z]+)$`
(0 false positives inside the VM gate on the current corpus).

**parentSessionId inheritance is NOT a cascade rule.** In this corpus the only
parented sessions are the 0-turn phantoms, which are filtered out before
inference — so an inheritance rule would have no inputs (the first draft's
"rule 11" contradicted the parse filter). Capture is retained for §14 only.

Both `inferProject` callers must be updated for the new return shape:
`discoverProjects.ts:67` AND `zombiesHeuristic.ts:214` (the latter reads
`inf.inferenceSource`). Widening is mechanical — `discoverProjects` already
passes full `UnifiedSessionEntry[]`.

## 5. Component 4 — trimmed provenance record

`UnifiedSessionEntry.projectAttribution = { resolvedVia: InferenceSource;
confidence: number }`. Just enough to answer "why is this session here?" in the
viewer and to drive the audit script. The full 13-signal record from the first
draft is cut (manifest bloat × 1199 + PII surface; the signals are recomputable
on demand). Viewer session detail shows `resolvedVia` + a "Move to a different
project" button that appends to `projectOverrides.json`.

**displayName collisions:** two routine task-ids (or two VM-USF basenames) can
resolve to the same `displayName`. The project ids differ, so data is correct,
but the UI must disambiguate — append a short id suffix (e.g. `Daily pulse
·a1b2`) when two projects in the list share a displayName. The
`projects.json` writer should detect and tag collisions so the viewer renders
them unambiguously.

## 6. Component 5 — overrides config

`apps/standalone/public/chat-arch-data/projectOverrides.json` (gitignored under
the existing `chat-arch-data/*` wildcard; also add an explicit enumerated line
+ PII label per the repo's `.gitignore` documentation convention). Match shapes:
`cwdGlob`, `sessionIds` (the only two needed — `gitOrigin`/`cloud` match zero
sessions). First match wins; rescan summary reports overlaps. This is the
manual escape hatch every comparable product (ChatGPT/Claude/Cursor Projects)
ships; here it sits on top of the transparent `resolvedVia` record. Fixes the
18-session `brycewatson.com` collision and any future irreducible case.

## 7. Migration — rebuild-from-scratch (no aliases, no re-key)

`projects.json` is regenerated every rescan (it already is — discoverProjects
runs unconditionally; EXPORTER_VERSION gates only the cowork/cli *caches*, not
inference). So new ids appear naturally on the next rescan. The only stale
artifacts are old per-project persona markdown (`analysis/personas/<old-id>.md`)
and LLM-derived narrative rows keyed to vanished ids.

Handling: documented one-time sweep via the EXISTING `/api/clear-personas` +
`/api/clear-narratives` endpoints, then a normal re-mine. **Skill-written
sidecars that persist across rescans must also be swept/re-mined:**
`curator-feed.json` (and `falsifier-verdicts.json`) are written by the
`/curate` + `/falsify` skills, not by `runAnalysis`, so they retain stale
projectId references until re-run — add them to the one-time sweep. By contrast,
kernel-built sidecars keyed on projectId (`project-trajectories.json`,
`archetypes.json`, `surprises.json`, topics) are rebuilt fresh by `runAnalysis`
every rescan and self-heal — no sweep needed. **No rename/re-key pass** — that
path risked many→one overwrite data loss (the VM collapse maps 282 ids → ~16)
and collided with the `narratives.json` two-writer CAS protocol. Rebuild
sidesteps both. **No alias system** — for a solo tool with no external
permalinks, surviving a one-time rescheme has no counted value, and the alias
mechanics had an unsatisfiable-for-splits threshold bug + an impossible
"Astro 301" (the route is `prerender=false`, the hosted target is static, and
existing redirects are client-side hash rewrites).

## 8. Dry-run / preview mode (new — rollback safety)

`pnpm exporter run start --project-identity-preview` (and a viewer affordance)
computes the new bucketing and writes `analysis/project-identity-preview.json`
(a diff vs current `projects.json`: counts, moved sessions, new/vanished ids)
**without** overwriting live artifacts. The user reviews before committing.
Cheap because the attribution record already exists.

**Adoption semantics (explicit):** there is no separate "commit" mutation —
adoption *is* the next normal rescan (the migration is rebuild-on-rescan, in
place). To prevent preview/live drift confusion, the preview file records the
input snapshot (manifest mtime + session count + EXPORTER_VERSION); the viewer
warns "preview is stale — corpus changed since it was generated" if the live
inputs no longer match before the user adopts. This is the rollback story:
review the preview, and if the new bucketing is worse, don't rescan (or restore
the prior `projects.json` from the preview's recorded baseline).

## 9. Versioning

Bump `EXPORTER_VERSION` 1.8.0 → **1.9.0** (additive optional fields; minor, per
the 1.6.0/1.7.0 precedent). The bump invalidates `cowork-sessions.json` /
`cli-sessions.json` caches so the new `scheduledTaskId`/`sessionType`/
`parentSessionId` fields repopulate on next rescan. **No `schemaVersion` bump** —
fields are optional and round-trip at schemaVersion 4 (`back-compat.test.ts`
covers 1-4). The "forward-version" protection is the compile-time TS
`schemaVersion: 1|2|3|4` union plus the back-compat round-trip tests, NOT a
runtime validator (unknown forward *keys* trigger `warnOnce` but the entry is
still emitted) — so adding optional fields trips nothing. `HEURISTIC_RECALL_VERSION`
untouched (corrections recall is unaffected).

## 10. PII & gitignore

- New entry fields (`scheduledTaskId`, `sessionType`, `parentSessionId`) are
  low-PII identifiers, not paths/content. No git-origin / absolute-path fields
  are added (those are deferred and, if ever added, must strip `user:token@`
  userinfo and be opt-in like `--enable-pr-join`).
- Add the new sidecars (`project-identity-preview.json`, `projectOverrides.json`)
  to the `.gitignore` enumerated documentation block; the `chat-arch-data/*`
  wildcard already covers them.
- No `.githooks/pre-commit` change needed: the populated-manifest detector keys
  on `"id":` + non-zero counts (pre-commit:~109,129), not on field names, so it
  already catches a populated manifest regardless of the new optional fields.
  (Verified — the first draft's "extend the detector" action item was
  unnecessary.)

## 11. Testability (all CI-runnable with fixtures)

Every component is unit-testable without the user's private corpus:
0-turn filter (synthetic ai-title JSONL fixture), cascade (synthetic entries
covering each rule + the VM-haiku guard), overrides (pure match function),
preview-diff (two in-memory `projects.json` inputs), back-compat (assert the
new optional fields round-trip at schemaVersion 4). Nothing here depends on
Ollama or filesystem walk-up (both deferred §14).

## 12. Definition of done — audit + adversarial validation (required)

`scripts/audit-project-identity.mjs` (precedent: `audit-correction-recall.mjs`):
asserts post-rescan targets — UNASSIGNED ≤ ~6 (with an enumerated reason
breakdown, NOT == 0; the residue is the zero-turn VM-haiku-no-USF sessions);
**gated-drop count == prior UNASSIGNED count (both 563)**; **no previously-
populated project loses sessions** (chat-arch keeps its 24 cwd-bearing 0-turn
sessions); **count(rule 2 fired) == count(sessions with `scheduledTaskId`)** (so
no scheduled session silently misses the routine bucket; assumes
`scheduledTaskId` ⊥ explicit `project` — true in corpus, since scheduled Cowork
manifests carry no `project` field — relax to ≥ if a counter-example appears); projects in [20,40];
singletons < 10; `proj_outputs` absent; ~15 routine projects present (assert on
`resolvedVia === 'scheduled-task'`, NOT an id-string prefix — the on-disk prefix
is `proj_routine-` after underscore normalization, see §4).
**Reason-distribution assertion** (not just count): emit UNASSIGNED with
`resolvedVia` and assert the reason breakdown, so a future real-but-unidentifiable
session (turns>0, no cwd, no title-match — currently 0 in corpus) surfaces
instead of hiding in a count. **Adversarial experiment** (per global CLAUDE.md):
construct cases where (a) the VM-USF rule over-merges two genuinely distinct
host folders sharing a basename, and (b) one `scheduledTaskId` spans multiple
date-prefixed per-run titles (verified real — assert displayName resolves
deterministically to the date-stripped stem) — assert the audit flags/handles
both. Run the script as the preview/commit gate.

## 13. Implementation order — 3 PRs (one per wave; CI is expensive)

Collapsed from 12 PRs (the per-PR split violated the project's
bundle-when-Claude-Code-implements convention). Subagent fan-out *inside* each.

- **PR 1 (atomic):** schema fields + parse-boundary filter + signal propagation
  + cascade v2 (incl. rule 0 override **match-function + `projectOverrides.json`
  consumption** — moved into PR 1 so the §12 adversarial experiment can actually
  exercise the over-merge mitigation, not just detect it) + trimmed attribution
  + BOTH `inferProject` callers updated + dry-run/preview mode + audit script +
  adversarial experiment + back-compat test. Preview does not flip live
  artifacts until reviewed.
- **PR 2 (atomic):** viewer "Move to project" affordance (writes
  `projectOverrides.json`, consumed by PR 1's match-function) +
  `resolvedVia` display + documented one-time persona/narrative sweep.
- **PR 3 (atomic):** version bump 1.9.0 + CHANGELOG `[1.9.0]` + CLAUDE.md
  (new fields, cascade order, new sidecars, sweep instructions).

## 14. Deferred (with explicit re-trigger conditions)

Genuinely valuable, but currently targeting uncounted / zero-signal failures.
Each ships the moment its data appears:

| Deferred component | Re-trigger condition |
|---|---|
| `gitRemoteOriginUrl`/`gitRoot`/`nearestManifest` walk-up + cascade rules | A future corpus shows generic-basename collisions beyond the single `brycewatson.com` case. Must be opt-in (`--enable-git-walkup`), strip userinfo, allowlist roots (never read arbitrary ancestor `.git/config`). |
| Cross-source canonicalization map | A counted case where the same project's basenames diverge across sources (worktrees, renamed VM folders). Must be regenerable (not monotonic-persisted) with an `unmerge` override. |
| projectId alias system | Only if external permalinks to `/projects/<id>` ever exist. Must define alias direction for 1→many splits and use client-side hash rewrite (no server 301 on static host). |
| Embedding-cluster UNASSIGNED rescue | Only if UNASSIGNED is nonzero after the 0-turn filter (audit will show). Must be fail-soft skip in CI + sticky-per-session assignment with hysteresis (the first draft's "deterministic" claim was metastable). |
| `cloudProjectUuid` cascade rule | Cloud sessions with declared Claude.ai Projects appear in the corpus. |
| Subagent attribution sidecar + viewer panel | Separate proposal (cost analytics, not identity). `parentSessionId` capture lands now so the data is ready. |
| SQL `sessions.project_id` reconciliation | Only after some path actually populates the `sessions` table — today `insertSession` has one caller (`seedFixture.ts`); the rescan never writes it, so reconciliation is currently a no-op. |
