# /falsify

You are the falsifier. /curate (or any generator-stage skill) just produced a list of findings — Narratives ranked for surfacing, candidate Patterns to encode, knowledge-debt clusters to install as rules. Each finding claims an `evidenceChain`: a list of session turns whose content supposedly supports the claim. Your job: read those turns and decide whether the citation is **valid** (the turn content does support the claim) or **invalid** (the turn doesn't say what the finding says it does).

**Status: scaffold.** This SKILL.md exists so Rev3-F F4 (falsifier verifier kernel) + F8 (meta-validation) have a stable invocation surface to wire into. Running this skill today reports "kernel not yet implemented" and exits cleanly.

## Why a separate skill (not just a /curate stage)

Plan §"Intelligence layer (generator / falsifier discipline)":

> "Two roles, separately invoked. Falsifier is structurally separate: different agent type, different system prompt, different prompt template. It verifies each generator finding's `evidenceChain` cites real session turns whose content supports the claim. Findings whose citations fail the falsifier are dropped before any user-visible surface."

The structural separation matters because the falsifier MUST NOT inherit the generator's framing of the claim. The falsifier reads the turns and asks "do these say what's claimed?" — independent of how persuasive the claim itself was. Mixing the two roles in one prompt biases the verifier toward the generator's frame; separating them is the smallest available control for that bias.

## When to invoke

- /curate calls /falsify per-candidate during its Stage 2 (`--no-falsifier` skips the call entirely and tags findings `'skipped-by-user'`).
- The user runs `/falsify --finding-id <id>` to manually re-verify a single finding (useful for spot-checking).
- Rev3-F F8 (meta-validation) samples N recent verdicts and re-judges them; that's also a /falsify invocation against a held-out set.

## Arguments

- `--data-dir <path>` [defaults to `./chat-arch-data`]
- `--finding-id <id>` [omitted] — verify a single finding by id. Without this, falsify reads a batch from a generator-supplied input file.
- `--input <path>` [omitted] — JSON file with `{ "findings": [{...}] }` (the curator's stage-1 output). Mutually exclusive with `--finding-id`.
- `--output <path>` [defaults to `${dataDir}/analysis/falsifier-verdicts.json`]
- `--request-id <uuid>` [omitted] — present when invoked from /curate; correlates status with the requesting flow.
- `--api-key-fallback` [false] — opt-in only (mirrors /curate's posture).

## Pipeline (scaffold — F4 implements)

### Stage 0 — Setup

1. Probe `claude --version` (F5). Exit cleanly on absent if `--api-key-fallback` is OFF.
2. Open the SQLite substrate via `@chat-arch/exporter/db`.
3. Resolve the candidate set (either the single `--finding-id`, or the batch in `--input`).

### Stage 1 — Per-finding verdict

For each candidate finding:

1. **Resolve the cited turns.** For every entry in `evidenceChain`, look up `(sessionSource, sessionId, turnIndex)` in `session_messages`. If any cited turn doesn't exist or is empty: verdict = `unavailable` (the citation itself failed). Don't infer — citation failure is its own bucket.

2. **Read the turn content.** Pull the full turn text (capped at `THRESHOLDS.curator.falsifierMaxCharsPerTurn` to prevent context-bloat — TODO: F4 adds the threshold).

3. **Ask: does this turn say what the finding claims?**
   - Prompt template (F4 will pin the exact text):
     ```
     The following finding was generated by chat-arch's narrative kernel:
       <finding.title>
       <finding.body>

     The finding cites this session turn as supporting evidence:
       <turn content>

     Question: Does the turn's actual content support the claim above?
     Answer in JSON: { "verdict": "supports" | "neutral" | "contradicts", "reasoning": "<one sentence>" }
     ```
   - Self-consistency: run K=3 (or `THRESHOLDS.curator.falsifierSelfConsistencyK` — TODO: F4) independent passes. Majority verdict wins. Disagreement triggers a third "ambiguous" tag.

4. **Aggregate across the finding's evidenceChain.** A finding's overall verdict is `verified` when ≥ `THRESHOLDS.curator.falsifierMinSupportRatio` of its cited turns came back `supports`. Otherwise `not-verified`. The unavailable bucket counts as a failure (citation hygiene matters).

### Stage 2 — Write verdicts atomically

Write `{ findingId, verdict, supportingCount, contradictingCount, unavailableCount, perTurnReasoning[] }` per finding to the output file via atomic tmp-file + rename (F7 helper — TODO).

### Stage 3 — Meta-validation hand-off (F8)

Sampled verdicts feed into the F8 rolling-window meta-validation. /falsify itself doesn't need to know — F8 reads the verdicts file independently and computes the Wilson lower bound against `THRESHOLDS.curator.falsifierAccuracyFloor`.

## What the falsifier MUST NOT do

- **Re-rank findings.** That's the curator's job. The falsifier returns per-finding verdicts; the curator decides which surviving findings make the top-K.
- **Generate new evidence.** The falsifier reads what's already there. If a finding's evidenceChain is sparse or weak, the verdict is `not-verified` — don't paper over it.
- **Compose with the generator's framing.** Each falsifier call is a fresh prompt. Don't reference what the generator said about the claim beyond what's in the finding's text.

## Plan billing posture

Same as /curate: `claude -p` first, `ANTHROPIC_API_KEY` opt-in only.

## Output framing

The falsifier reports VERDICTS, not value judgements. "Verified" doesn't mean "useful"; it means "the cited turns support the claim." The curator decides usefulness based on the verdict + tier + correlation. Keep the falsifier's voice neutral — it's an auditor, not an editor.
